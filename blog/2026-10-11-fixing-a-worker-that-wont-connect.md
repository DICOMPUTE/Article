As more hobbyists ran inference nodes in 2026, self-service troubleshooting
guides became essential. This post turns the
[troubleshooting docs](/docs/provider/troubleshooting) into a triage order: run
one command, read what it says, then follow the symptom.

One thing to settle first, because it is the most common false alarm. **A
worker that is connected, passes its checks and shows zero requests is normal
today.** The fleet path carries real traffic for one internal test account only
([operate page](/operate)). If your problem is "it connects but nothing is
happening", jump to that section below. The rest of this post is about workers
that genuinely cannot connect or refuse to start.

For the background on install and join, see
[Running a DiCompute provider node](/blog/running-a-dicompute-provider-node).

## Start with dico-agent doctor

`dico-agent doctor` runs a series of independent checks, and one failure never
hides another. Run it before anything else. Two useful variants:

```bash
dico-agent doctor --offline        # skip the checks that need the coordinator
dico-agent doctor --json report.json   # write the same report to a file you can attach
```

`--offline` skips the five checks that reach the coordinator's network, prints
an explicit SKIP for each instead of waiting on a timeout, and still runs the
local ones: identity, credentials, hardening, the engine hop and disk space. It
is the right tool for a box that has dropped off the fleet. Not everything is a
failure either: many checks can only warn, and a warn is information, not a
fault.

One exception: a coordinator URL that uses plaintext to a non-loopback host
stops every subcommand before `doctor` can run. See the coordinator URL section below.

## "No worker credentials found": finishing login

`dico-agent start` says it found no worker credentials when you never completed
`dico-agent login`, or the login never received an approval. Run it and wait
for it to finish:

```bash
dico-agent login
```

The device-code login prints a link. You open it, sign in, and approve the
machine. If it hangs at "Waiting for approval", the approval has not
happened yet. Complete it in the browser you signed in with.

Related cases from the docs:

- **Credentials and identity must travel together.** The credentials file is
  tied to the identity keypair it was issued for. Copy only the credentials file
  to a new box and `doctor` reports a mismatch. Copy both files from the same
  install, or run `dico-agent login` fresh, which makes a new identity that
  needs a new approval.
- **Gateway admission failures.** If the gateway refuses the worker's hello
  repeatedly because of a stored credential it rejects, the agent slows to one
  retry every five minutes. The fix the docs give is to re-link the box:
  `dico-agent logout --local-only --yes && dico-agent login`.
- **Connection closes with key-mismatch.** The coordinator pins your worker id
  to the signing key it saw first. If `identity.json` was regenerated by a fresh
  install, a restore that missed it, or a deletion, the key no longer matches.
  You cannot fix that from your side; the docs say to contact whoever operates
  the coordinator.

## Coordinator URL, pins and clock skew

- **Plaintext URLs are refused.** The agent exits on startup if the coordinator
  address uses `ws://` or `http://` to a host that is not loopback. Use `wss://`
  or `https://`. The only exception is `localhost` or `127.0.0.1` for local
  development. There is no override flag for this.
- **Coordinator pin.** A warning that no pin is set means the link is protected by TLS
  but does not authenticate which coordinator is on the other end.
  It is a warning, not a failure.
- **Clock skew.** A real fail here means your clock is more than a minute off
  the coordinator's. The consequence the docs name: receipts are dropped as
  outside the time window. The fix is to repair NTP or the system clock.

## Model integrity and engine model-id mismatch

Two checks guard what you advertise against what you serve:

- **Model manifest.** A real failure means your local weight hash no longer
  matches the hash published for the model. `dico-agent start` runs the same
  check before opening the serving connection, and refuses to boot on a real
  failure. Confirm that your weight path points where you think it does. If you
  changed models or quantization on purpose, republish the manifest your
  coordinator serves.
- **Model quantization.** A failure means your declared quantization disagrees
  with the file's own header, usually the wrong file or a stale config.
- **Engine model-id mismatch.** If `ENGINE_MODEL_ID` differs from `MODEL_ID`,
  `start` prints a loud `[engine-model-guard]` warning and keeps running. The
  worker would advertise one model while sending requests to an engine model
  with another name. Fix one of the two values. If your engine genuinely
  registers the model under a different name, `MODEL_ALIAS_ALLOW` lists the
  allowed alias.

## Memory, context window and disk space

- **Memory and context window.** Most of these checks only warn. For example,
  a declared context window that disagrees with the weight file's own metadata is
  a warning about a stale config or the wrong file.
- **Disk space.** The general disk check is informational. The *model weight
  disk space* check, when a weight root is configured, has hard thresholds: the
  docs say it fails when free space drops under 1 GiB and warns under 20 GiB.
  Reclaim space with `dico-agent remove-model <id>` or
  `dico-agent remove-model --orphaned`, or point the weight root at a bigger
  volume.
- **Stale update leftovers.** Staged binary files from an interrupted install
  can sit in the install directory. Delete them or re-run the installer, which
  sweeps them.
- **Competing inference.** Another engine, such as one on a well-known port,
  sharing the box can halve throughput and drift memory checks. Doctor warns
  about it.
- **Service version.** If the running service reports a different version than
  the installed binary, run `dico-agent restart --wait`.

## Connected but zero requests: normal today

The docs say it directly: a connected, doctor-clean, heartbeating worker with
zero requests is the expected state today. No live traffic is routed to any
third-party worker on this path. This is not a fault and no setting fixes it.
Do not reinstall, re-link or tune anything because of it. Check
[operate page](/operate) for the current status.

## Sharing logs with support safely

When doctor does not explain it, send support a bundle instead of a screenshot.
The [sharing-logs docs](/docs/provider/sharing-logs) cover this:

```bash
dico-agent logs upload --dry-run     # print the size, redactions and exact text; sends nothing
dico-agent logs upload               # sends it and prints a report id
```

The dry run needs no login. A bundle is the tail of your `agent.log`, run
through a redaction pass for secret-shaped strings and for things like your
username, home directory and private addresses. The docs state the limits: the
redaction is a floor and not a guarantee, and the one case where a crash could
leave prompt content in a log line is documented as a known limit. Read the dry
run before you send.

Afterwards, reference the report id. `dico-agent logs reports` lists what the
coordinator holds with a retention countdown, and `dico-agent logs withdraw
<reportId>` deletes a bundle you no longer want held.
